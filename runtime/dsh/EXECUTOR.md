## Owner configuration

Set `BANG_ORGANIZER_DSH` before starting the native project Runtime:

```json
{"version":1,"executable":"ABSOLUTE_NATIVE_LAUNCHER","prefixArgs":[],"model":"deepseek-flash","credentialStore":"ABSOLUTE_AUTHORIZED_VERSION_1_STORE","inheritProxy":false,"electron":false}
```

The pinned launcher must report exactly `0.2.1-rc.2`. `prefixArgs` supports a trusted native launcher, not browser-supplied commands. Windows desktop uses its installed Electron executable with `electron:true` and `--expose-internals`, followed by the shipped `@deepseek-ai/dsh-desktop-host/lib/cli.js`, exactly as its `dsh.cmd` launcher does. Linux uses native Node plus the official pinned `@deepseek-ai/dsh/lib/bin.js`. `.cmd`, `.bat` and `.ps1` executables are rejected. Ambiguous native/Codex/DSH owner settings fail before dispatch.

The provider is explicitly **deepseek-official** (API-key route). It never silently switches to `deepseek-account`, another provider or another model. GUI account sign-in is independent of this headless authorization. The reviewed overlay is generated by `restrictedOverlay` in `executor-config.mjs`; it can be inspected before using a configuration. Optional `credentialStore` is passed to DSH's supported credentials-local `path` setting with `watch:false`. Bang never copies credentials or returns their contents. A version-1 store boots without migration. Older stores may be migrated by DSH itself, so establish format through nonsecret status before authorizing that path; no read-only/no-migrate option exists in this pinned provider. Do not alter store permissions or bypass its owner-only check to make a probe work.

Every attempt has a fresh child-only DSH_HOME and cwd inside the native worker directory. This avoids the launcher's generated-profile rewrites in the normal home. No user profile, settings, project `.env`, project instructions, MCP, skills or inherited API-key variables are included. `inheritProxy:true` uses the existing native allowlist of proxy environment names; their values never enter arguments, tasks or logs. Existing authentication is consumed only by the official provider. No credential/configuration editing tool is exposed.

## Restrictions and result contract

The profile disables tool registrations, plugin management, subagents, PTC/workflow, goal drivers, instruction discovery, auxiliary title/compaction model calls, provider retries and telemetry. It uses native tool presentation, read-only sandbox policy and no approval escalation. A monotonic tool guard denies execution; before every model step the guard additionally verifies zero visible schemas and checks the selected API-key reference with public `credentials.describe`, which returns no secret. Actual pinned wire audits independently verify `tools:[]`. No project path, write API or runtime capability is supplied to the model. The trusted local adapter/plugins are not an OS sandbox against malicious owner executables.

Input uses stdin. Output requires successful process exit, one matching started/terminal turn with `reason.kind=completed`, final JSON, no tool projection, and the common candidate validation. A final-looking JSON line by itself cannot publish. Failed/mixed terminals, nonzero exits and malformed candidates fail closed. Model-authored usage is rejected; available step usage is summed and omitted if any step lacks it. The shared provider grammar is imported from `runtime/codex/result-schema.mjs`; Coordinator remains responsible for source IDs, conditions, human authority, dependency fences, compilation and sole publication. No separate knowledge store/tables were introduced.

The native supervisor owns the adapter and launcher descendants using Windows Jobs / Linux process groups. Cancellation, timeout, budget, retries, pause-on-auth/budget, attempt fencing and cleanup use ticket17's common lifecycle. Provider streams/reasoning/stderr stay bounded in memory and are discarded; receipts retain only fixed error codes/stage/reason. No billing-cancellation claim is made.
