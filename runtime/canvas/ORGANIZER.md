# Incremental Organizer — ticket 15

## Public contract

The native owner accepts `organizer-enable` and `organizer-status` with JSON stdin `{topicId}`. Protected HTTP exposes `POST /api/canvas/:topic/organizer-enable` and `GET /api/canvas/:topic/organizer`. Explicit enable persists per topic. Received pending versions are consumed in order; no browser is required. A failed task blocks subsequent organization of that topic, while receiving, manual saves and other topics remain available. Retry/budget/lifecycle controls belong to ticket 16 and later.

For controlled development, set `BANG_ORGANIZER_ENDPOINT` **before starting the native owner** to a trusted loopback HTTP JSON service. There is no client-supplied shell command, executable, destination, credentials or endpoint. Redirects/non-loopback destinations are rejected. This adapter is a controlled-model boundary, not evidence of real Codex/DSH execution. It invokes no model tools and grants no board-writing API. Deployment of a real external executor belongs to the executor/host tickets. No service fallback is attempted.

The Executor receives `{version:1,policy,completedTurns,activeContext}`. CompletedTurns retain exact durable source ID/version/hash and primary final text. Active context contains up to 100 knowledge cards in committed order, their metadata, visual regions separately, and only relations with knowledge endpoints. Unconverted annotations never become model facts. The full committed state remains the publisher/compiler baseline; limiting context never deletes unseen cards. This initial deterministic selection is not a relevance-ranking or quality benchmark claim.

Result: `{version:1,changes:[...]}`. Allowed changes are `create-card` (`id,text`), `edit-card` (`id,text`, only non-manual discussion text), `supplement-card` (`id`, compatible evidence without replacing text), and `create-relation` (`id,fromNode,toNode,label`). Every change requires `conditions:string[]`, `uncertainty:string`, and nonempty `sources:string[]` referencing this task's actual CompletedTurn. All other fields/operation types are rejected. The model cannot supply author, baseline, task identity, geometry, executable instructions, deletion, global replacement or arbitrary metadata. Empty changes acknowledge processing without creating a board revision.

## Coordination, publication and status

Each task has independent task/attempt/Runtime epoch identities. Preparation snapshots source and read context in a short owner-queue operation. **The HTTP model wait is outside the owner queue and all SQLite transactions.** Final validation and common publication re-enter that queue. A bounded 120-second transport timeout and 1 MiB output ceiling are transport safety only; project-wide concurrency, hourly budget and retries remain ticket 16.

The coordinator checks the full semantic fields and knowledge metadata of its read subgraph, even when the result writes elsewhere. A newer received answer version invalidates an older running inference. Geometry changes remain compatible. Current manual text cannot be replaced; compatible evidence supplements retain manual provenance, old conditions, old uncertainty and source IDs. Deleted identities and deleted relations are not resurrected. Relations to visual groups are rejected. The existing deterministic local compiler places only additions and keeps prior geometry/stacking/unseen state; diagnostics are retained on the task.

Only `store.mjs`'s existing prepared-intent publisher writes Canvas/revisions. Organizer provenance, conditions, uncertainty and source IDs are in the same committed revision. Task acknowledgement updates the durable ingestion queue and source backlog in one SQLite transaction after publication. On restart, confirmed publisher receipts complete interrupted acknowledgements; other old attempts lose commit eligibility and preserve pending sources. Ordinary status excludes full input/baseline; failure messages use stable categories without prompts. The UI polls receipts independently of displayed revision, and new knowledge requires manual refresh.

Backup snapshots include Organizer settings/tasks but disable organization and remove active input/baseline in the exported copy. Running attempts become interrupted failures; restored sources remain frozen. The original project continues independently. Backup inspection rejects enabled or running imported authority.

## Ticket 31 structure extension

The existing version-1 result additionally accepts `structure:{version:1,kind:"classification"|"radial",rootId}` on `create-card` only and `kind:"classification"|"general"` on `create-relation` only. The versioned `structureRules` input explains relation definitions, examples and safe migration. Existing card structure stays protected and is a read dependency even though changing it preserves knowledge provenance. The Compiler resolves coordinates; the model never supplies geometry. Both new and existing roots must be knowledge in the active/new set and the root must share the intent. Uncertainty defaults to free layout; visual grouping is never evidence of classification. Controlled executor/public Runtime and real editor evidence is recorded under Ticket 31 in README.md; real model quality remains ticket 43.
